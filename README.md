# Project OMNISCIENT — Technical Manual

An auditable agentic detective system that solves murder mysteries by interrogating LLM-based suspect agents and producing a fully transparent, step-by-step case report.

---

## System Architecture

```
┌─────────────────────────────────────────────────────────────────────────┐
│                              main.py                                    │
│  Entry point. Loads dataset, initialises agents, runs investigation.    │
└──────────────┬──────────────────────────────────┬───────────────────────┘
               │                                  │
               ▼                                  ▼
┌─────────────────────────┐          ┌────────────────────────────────────┐
│    SuspectAgent ×N      │          │         ReasoningEngine            │
│  Gemini (cloud)         │◄─────────│  Part 2 — Investigative Loop       │
│  Maintains character    │  goal    │                                    │
│  over full context      │ question │  • Bayesian suspicion scores       │
└────────────┬────────────┘          │  • IG-based question selection     │
             │ raw answer            │  • Contradiction detection (Tier1) │
             ▼                       │  • Entropy tracking                │
┌─────────────────────────┐          │  • Formal terminal conditions      │
│      Interrogator       │ testimony└────────────────────────────────────┘
│  Part 1 — Detective     │──────────►
│                         │          ┌────────────────────────────────────┐
│  • Question generation  │          │       ReportGenerator              │
│    (local Ollama LLM)   │          │  Part 3 — Case Report              │
│  • Claim extraction     │          │                                    │
│    (structured JSON)    │          │  • Deterministic sections 1–3, 5–9 │
│  • Persona stability    │          │  • One LLM call for narrative      │
│  • Follow-up logic      │          │  • Token cost reporting            │
└─────────────────────────┘          └────────────────────────────────────┘
```

### Component Interactions

1. `main.py` loads a case, builds `SuspectAgent` objects (Gemini), and initialises `ReasoningEngine` with data-driven priors derived from the `suspicion` observation count.
2. The main loop calls `ReasoningEngine.next_goal()` → `Interrogator.conduct_session()` → `ReasoningEngine.ingest_testimony()` → `ReasoningEngine.check_termination()`.
3. After the loop, `ReportGenerator.generate()` assembles the full case report.

### LLM Role Separation

| Role | Model | Why |
|---|---|---|
| Suspect agents | Gemini (cloud) | Needs reliable long-context character retention across many turns |
| Detective (question generation) | Local Ollama `qwen2.5:7b` | Fulfils local LLM requirement; no rate limits |
| Parser (claim extraction) | Local Ollama `qwen2.5:7b` (fine-tunable) | Same local model; fine-tuned for structured JSON output |
| Narrative reconstruction | Gemini (cloud) | Single end-of-case call; benefits from stronger reasoning |

If Ollama is unreachable at startup, the detective automatically falls back to Gemini with a warning in the log. This allows development before the local model is set up.

## Methodology and Design Choices

### Part 1 — Interrogator Agent

**Testimony format: JSON semantic triples**

Each suspect response is parsed into a list of `Claim` objects:
```
claim_type  : alibi | accusation | denial | relationship | knowledge | inconsistency
subject     : who the claim is about
predicate   : action or relationship (snake_case)
object_     : what the predicate points to
time_ref    : time reference string or null
confidence  : stated | implied | uncertain
source_text : verbatim grounding fragment
```

This format was chosen over raw propositional logic or free-text because:
- Contradiction detection is an exact Python dict lookup, not an NLP problem.
- Bayesian updates are triggered by specific `claim_type` values deterministically.
- Claims are human-readable and directly quotable in the case report.
- The schema is a closed vocabulary — no hallucinated field names.

**Persona stability**

The detective persona (ANALYTICAL / SYMPATHETIC / HOSTILE) is embedded in the system prompt once at session construction via `build_interrogator_system_prompt()`. It is never injected as a runtime instruction such as "You are now hostile." Runtime injection degrades over long contexts as attention dilutes the instruction. System-prompt embedding anchors the model's generation distribution from the first token and remains stable for the full session.

**Fine-tuning**

`train_parser.py` fine-tunes a local LLM (default: `unsloth/Llama-3.2-3B-Instruct`) using LoRA on (question, answer) → structured JSON claim pairs generated by `generate_training_data.py`. The fine-tuned model is served via Ollama and replaces the base `qwen2.5:7b` as the parser client. The detective question-generation role continues to use the base model.

**Communication protocol**

```python
# ReasoningEngine -> Interrogator
InterrogationGoal(suspect_name, objective, persona, time_window, known_conflicts, max_turns)

# Interrogator -> ReasoningEngine
Testimony(testimony_id, suspect_name, objective, persona_used, turns, claims,
          emotional_tone, evasiveness_score, parse_error, parse_error_detail)
```

The Interrogator is **semi-autonomous**: it executes the engine's suggested objective but autonomously decides whether to ask a follow-up question based on claim quality (zero claims → likely evasive, uncertain confidence → needs clarification).

### Part 2 — Investigative Loop

**Bayesian suspicion scores**

Each suspect starts with a prior derived from the number of `suspicion` field observations in the dataset (0 observations → 0.35, 5+ → 0.70). After each testimony, a deterministic weight table (`SUSPICION_WEIGHTS`) is applied:

| Event | Delta |
|---|---|
| `alibi_provided` | −0.08 |
| `alibi_corroborated` | −0.22 |
| `alibi_contradicted` | +0.30 |
| `motive_established` | +0.18 |
| `accused_by_another_suspect` | +0.20 |
| `evasiveness_high` | +0.12 |
| `denial_recorded` | −0.05 |

Every update is logged as a `SuspicionEvent` with timestamp, event type, delta, score before/after, and a plain-English justification. This produces the complete audit trail in Section 6 of the case report.

**Information Gain heuristic (question selection)**

For every valid `(suspect, objective)` pair, the engine computes:

```
ig_score = base_ig(objective, known_coverage)
           × priority_weight(suspicion_score)
           × diminishing_returns(sessions_done)
```

Where:
- `base_ig` is 0.0 if the objective's coverage gap is already filled (e.g. alibi already extracted), otherwise a type-specific constant (contradiction confrontation = 1.5, motive = 0.90, alibi = 0.85, open-ended = 0.65).
- `priority_weight = 0.25 + 0.75 × score` (high-suspicion suspects get more attention).
- `diminishing_returns = 1 / (1 + sessions × 0.45)`.

The pair with the highest `ig_score` is selected. This is computed entirely in Python with no LLM calls.

**Contradiction detection**

Two-tier rule-based system:
1. **Location conflict**: same subject + same predicate + overlapping time_ref + different object_ → contradiction.
2. **Corroboration conflict**: suspect A names suspect B in their alibi + suspect B issued a denial.

Both tiers run in O(n²) over extracted claims after each testimony. When a contradiction is detected: it is logged, the contradicted suspect's `alibi_contradicted` weight is applied (+0.30), and a `CONFRONT_CONFLICT` goal with the contradiction description embedded is queued with the highest IG score in the next selection round.

**Terminal conditions**

| Condition | Trigger |
|---|---|
| **T1 — Conviction** | `max_score ≥ 0.75` AND `separation ≥ 0.20` AND no unresolved contradictions for top suspect |
| **T2 — Entropy stagnation** | `≥ 6 sessions` AND entropy reduction over last 3 sessions `< 0.03` bits |
| **T3 — Unsolvable** | Total sessions `≥ 20` |
| **T4 — Inconclusive** | All suspects seen `≥ 2` times AND `separation < 0.20` |

Entropy is computed as the Shannon entropy of the normalised suspicion score distribution after each session.

**Persona selection**

The engine selects the persona for each goal based on the suspect's current state:
- `HOSTILE` if score > 0.60 or maximum evasiveness ≥ 3.
- `SYMPATHETIC` if score < 0.30.
- `ANALYTICAL` otherwise.

### Part 3 — Case Report

The report is assembled from nine deterministic sections plus one LLM call:

1. Case overview (static metadata)
2. Verdict with accuracy check
3. Suspect summary table
4. **Chronological reconstruction** — one Gemini call (~400 tokens), fed with the verdict, top suspect's claims, and all contradictions. Falls back to a rule-based summary if the call fails.
5. Full investigation timeline (all sessions, all turns, all extracted claims)
6. Reasoning trace (every `SuspicionEvent` in timestamp order)
7. Contradictions detected and resolution status
8. Errors and anomalies
9. Computational cost (sessions, turns, tokens, elapsed time)

## Setup and Execution Guide

### Prerequisites

- Python 3.10 or later
- A Gemini API key ([get one here](https://aistudio.google.com/apikey))
- At least 8 GB of RAM for the local LLM (16 GB recommended)

### 1. Install everything

```bash
chmod +x setup.sh
./setup.sh
```

`setup.sh` installs Ollama, starts the service, pulls `qwen2.5:7b`, installs Python dependencies, and creates `.env` from `.env.example`.

### 2. Configure environment

```bash
# Edit .env and set your Gemini API key
nano .env
```

```
GEMINI_API_KEY=your_key_here
```

### 3. Run an investigation

```bash
# Case index 0 (first case in dataset.json)
python main.py 0

# Case index 42
python main.py 42
```

The case report is written to `reports/case_<index>.txt`. Logs are written to `logs/case_<index>.log`.

### 4. Manual dependency installation (alternative to setup.sh)

```bash
# Install Ollama
curl -fsSL https://ollama.com/install.sh | sh

# Start Ollama and pull the model
ollama serve &
ollama pull qwen2.5:7b

# Install Python dependencies
pip install -r requirements.txt
```

### 5. Optional: Fine-tune the local parser

```bash
# Install fine-tuning dependencies (requires CUDA GPU, 8+ GB VRAM)
pip install -r requirements-finetune.txt

# Generate training data from the training split
python generate_training_data.py

# Generate validation data
python generate_training_data.py --split val

# Fine-tune the local parser model
python train_parser.py

# Load the fine-tuned model into Ollama
ollama create omniscient-parser -f parser_model_finetuned_gguf/Modelfile

# Update .env to use the fine-tuned parser
echo "DETECTIVE_MODEL=omniscient-parser" >> .env
```

## Logging and Exception Handling

All modules use Python's standard `logging` library with the format:

```
%(asctime)s | %(levelname)-8s | %(name)s | %(message)s
```

Every LLM call failure is caught and logged at `ERROR` level. Session failures do not terminate the investigation — the engine skips the session and selects the next goal. Parse errors are logged and recorded in the `Testimony.parse_error` field, which surfaces in Section 8 of the case report.
